# xdw-salvage

DocuWorks 形式（`.xdw` / `.xbd`）のコンテナ構造を読み、**ベンダー製品なしで取り出せるものを取り出す** Rust クレートです。依存クレートはゼロ、`unsafe` なし、Windows / macOS / Linux で同じ結果になります。

内部構成は、文書・復元結果を持つ `domain`、ポート経由でユースケースを組み立てる `application`、XDW/LZH/EMF・ファイルシステムの具体実装を持つ `infrastructure`、PDF/HTML/CLI のアダプターに分かれています。詳細は [`docs/architecture.md`](docs/architecture.md) を参照してください。

> **非公式ツールです。** FUJIFILM Business Innovation とは無関係で、同社の承認・支援・提携を一切受けていません。DocuWorks は同社の製品名です。

## 取り出せるもの

| 対象 | 結果 |
|---|---|
| ページ上の画像 | 無劣化。バイト単位でそのまま（写真・図版は素の JPEG で入っている） |
| 同梱された元ファイル | `.docx` / `.xlsx` / `.pptx` / 旧 Office / PDF を正確に切り出し |
| ページ台帳 | **本当の枚数**・用紙寸法・画素数・格納形式 |
| 変換後の期待値 | 「本来何ページ・どの用紙寸法か」を出力し、他ソフトの変換結果を監査 |
| ページ本文 | コンテナの符号化を展開し、中の EMF から**検索できるテキスト**として復元 |
| ページの図版 | メタファイルが指定する**元の位置・原寸**で配置（背景タイル・画面キャプチャなど） |
| 罫線・塗り | ブラシ塗りの矩形として復元（帳票の罫線はこれ） |
| PDF | 上記から組み立て。取り出せないページは位置合わせ用の注記ページ |
| HTML | 1 文書 = 1 ファイル。画像も元ファイルも中に入るので、これ 1 つで完結する |
| PDF / HTML への同梱 | 見つけた元ファイルを添付として持たせ、原本が変換物と一緒に動くようにする |
| 復号できないストリーム | 残った稀な 1 本を書き出し、申告された展開後サイズ付きの CSV を添える |
| 拡張子が嘘のファイル | 中身を見て名指しする（`.xdw` という名の PDF・docx・JPEG など） |

プリンタドライバ経由で作られたページは、**ベクタ／文字の層が独自の符号化**で入っています。
**本クレートはこれを復号します。**

> **文字も戻ります。**
> このベクタ／文字層の符号化は **LHA `-lh5-`**（LZSS ＋ ブロックごとの静的ハフマン表）で、
> 展開すると **Windows 拡張メタファイル（EMF）** が出てきます。
> 文字は `EXTTEXTOUTA` レコードに **CP932 の文字コードと座標**で入っているので、
> **検索・コピーできるテキストとして取り出せます**。
> 手元の 28 文書では **1,406 ページ中 1,397 ページ（99.4%）** が再現でき、
> **158 万字**が取れました。詳細は `docs/coding.md`。

### 大きな図版は「帯」に切られています

大きな画像は 1 枚では格納されません。プリンタドライバが**同じ幅の横帯に刻んで**、
1 帯 1 エントリで書き込みます。ある実ファイルでは 1 枚の図面が **691 枚の帯**になっていました。
帯を 1 枚ずつ並べても読めません。

本クレートは**連続する同じ幅の帯を 1 枚の画像として隙間なく連結**します。
上記の 691 枚は **10 枚の読める画像**になります。
連結した塊は**行揃えで敷き詰めて**シートを使い切ります。
縦長の塊はシート単位でまとめて 90 度倒すので、紙を一度回せば読めます
（元の配置・向きではない旨は出力に明記します）。

**何がどこまで戻るのか**は、実ページの見た目と突き合わせて確認済みです。
回収した 3 枚の帯は、ページ上の連続した 1 本の帯（高さの 12.6%）にぴたり一致しました。

ベンダー製 PDF が手に入った 1 冊で、**1 ページずつ実機と突き合わせて**います。
2 ページ目は全面テキストで、**取り出した文字は実機の PDF と 100.00% 一致**しました（689 字、欠落ゼロ）。

### 実寸で描きます

帯の幅がページ幅と一致するとき、`幅[px] ÷ 用紙幅[mm]` が妥当な印刷解像度になれば
（文書 A は 572 dpi）、**ページ上の実寸が確定**します。失われるのは上下位置だけです。
この条件が成立するとき、本クレートは引き伸ばさず**実寸で**描きます。

### ページ表には 3 種類のものが混ざっています

コンテナのページ表には、**シート・その縮小画像・シートの上に載っている画像**が並んでいます。
全部をページとして数えると、**1 ページのパンフレットが 4 ページの文書になります**。

見分け方は並び順です。コンテナは「シート → そのシートを構成する画像 → シートの縮小画像」の順に書きます。
つまり**縮小画像が来る前に現れた、用紙寸法を持たないエントリは画像**であり、
縮小画像より後のものは独立したシートです（写真から取り込んだページがこれにあたります）。

この読み方は容器自身が裏付けています。手元の 23 ファイルすべてで、
**シートの枚数と縮小画像の枚数が一致**し、**画像エントリは必ずシートとその縮小画像の間**にありました。

### ページ表には平文のデータ表も混ざっています

シート・縮小画像・画像のほかに、**`[長さ][値]` を並べただけの平文のデータ表**が入っていることがあります。
`dpi` `mm` `org` `%100` といった短い名前を持つもので、画像ではありません。
これをページとして数えると**実在しないページが 1 枚増えます**（実サンプルで 6→5、4→2 の誤りがありました）。
`info` は名前を読み出して表示します。

パスワード保護・電子署名付きの文書は**読みません**。これらは後続のコンテナ世代で書かれるため、対応世代の範囲外として拒否します。アクセス制御を迂回する機能は実装しておらず、今後も実装しません。

## 使い方

```
cargo install xdw-salvage
```

```
xdw-salvage info    <FILE>...              構造とページ台帳を表示
xdw-salvage extract <FILE>... -o <DIR>     JPEG ページと同梱元ファイルを書き出す
xdw-salvage pdf     <FILE>... [-o <OUT>]   取り出せるページで PDF を組む
                                           （複数指定時 -o は出力ディレクトリ）
xdw-salvage html    <FILE>... [-o <OUT>]   同じ内容を自己完結 HTML 1 枚で出す
xdw-salvage codec   <FILE>... -o <DIR>     復号できないストリームを書き出す

主なオプション：

- **`--font <path.ttf>`** — ページ本文に使う TrueType フォントを PDF に埋め込みます。
  指定しない場合は標準の日本語フォント名を書くだけなので、**その書体を持たない環境では表示されません**。
  配布先を選ばない PDF にしたいときは指定してください（フォントは同梱していません。手元のものを指定します）。
- **`--no-decode`** — ページ本文を展開せず、従来どおり注記ページを置きます。
xdw-salvage triage  <PATH>... [-o <CSV>]   資産全体を仕分けして CSV に出す
xdw-salvage manifest <FILE>... [-o <CSV>]  変換後に何ページあるべきかを出す
xdw-salvage verify  <FILE.xdw> --pages <N>  変換結果のページ数を照合する
```

### `pdf` の出力について

- **取り出せたページは無劣化**。JPEG ストリームを `DCTDecode` としてそのまま埋め込むので、PDF から取り出したバイト列は原本と一致します
- **取り出せないページは注記ページ**にして、元文書とページ番号がずれないようにします（`--skip-missing` で除外可）
- **元ファイルを PDF に添付**します。閲覧ソフトの添付ペインに出るので、変換物と原本が一緒に動きます（`--no-attach` で無効化）
- **`--lang ja`** で注記を日本語にします。日本語フォントは埋め込まず標準の文字コレクションを指定するためファイルは小さいままですが、フォント設定のない閲覧環境では描画されません。**そのため常に英字の 1 行を併記します** — 真っ白なページになるより良いので
- **`--paper a4`** で全ページを同一用紙に揃えます。画像は中央配置・縮小のみ（拡大しないのでボケません）
- **取り出せなかったページにしおりを付けます**。163 ページ中 139 ページが穴、といった文書を目視で追うのは無理なので、しおりから直接飛べます（`--no-bookmarks` で無効化）
- **注記のページ番号は PDF のページ番号と一致します**。コンテナの通し番号は縮小画像も数えるため、そのまま使うと 139 枚目に「139 ページ」ではなく「319 ページ」と書かれてしまいます
- **複数ファイルを一度に変換できます**。`-o` にディレクトリを渡せば、数千件の移行を 1 回のコマンドで回せます
- 文書情報に「何ページ中何ページを回収したか」を記録するので、PDF 自体が自分の完全性を語ります
- **`--carry-source`** で、`.xdw` そのものを出力に添付します。ほとんどのページが復号できない資産では、
  注記ページだけの PDF は移行とは言えません。原本を中に抱えていれば、
  少なくとも**元ファイルの上位集合**になります（読めるところは読め、それ以外は必ず元に戻せる）。
  サイズはおよそ倍になるので既定では無効です。`html` でも同じオプションが効きます

### `html` の出力について

PDF と同じ内容を、**外部ファイルを一切参照しない HTML 1 枚**で出します。画像は data URL、
同梱されていた元ファイルはダウンロードリンクとして本文に入るので、共有もアーカイブもこれ 1 つで済みます。

- ページ番号は PDF と同じ規則で、取り出せなかったページは枠だけのカードになります（`--skip-missing` で除外可）
- 冒頭に「復元できなかったページ」の番号が並び、そこから直接飛べます
- 明暗どちらの表示設定でも読め、印刷時はカード枠が消えます
- ファイル名は本文に埋め込む前にエスケープします。`.xdw` の名前は利用者が付けたものなので、信用しません
- 帯に刻まれた図版は隙間なく連結して 1 枚として表示します（PDF と同じ規則）

### 出力ファイル名の衝突について

`Note.xdw` が 9 つのフォルダにある資産を 1 つの出力ディレクトリに変換すると、
ファイル名で書くと 8 つが黙って消えます。**これはこのツールが検出しようとしている種類の損失そのもの**なので、
2 つ目以降には `~2`, `~3` を付けます。`extract` / `pdf` / `html` / `codec` すべてで同じ規則です。

### 拡張子が嘘のファイルについて

資産を一括で舐めると、**`.xdw` という名前の PDF** が出てきます（実サンプルで遭遇しました）。
「コンテナヘッダがありません」とだけ言われると、ありもしない不具合を探すことになるので、
**中身を見て名指しします** — PDF / docx / xlsx / pptx / 旧 Office / JPEG / PNG / TIFF / RTF / マークアップ。
`triage` では `OTHER` として 1 行に記録するので、**移行対象から外すべきファイルが一覧に残ります**。
推測はしません。先頭バイトで断定できるものだけです。

### `manifest` / `verify` — 移行の独立監査

一括変換で一番怖い失敗は「何ページか静かに落ちる」ことです。変換したソフト自身は自分の失敗を報告できません。

本クレートが担うのは、**他では得られない側だけ**です。コンテナのページ表から「本来何ページあるべきか」を読み出します。変換後の PDF を数えるのは、既にお使いの PDF ツールに任せてください。**PDF の読み取りは本クレートの仕事ではありません** — ここで二つ目の PDF パーサを抱えても、監査自体が間違う経路が増えるだけです。

```
$ xdw-salvage manifest 稟議書.xdw
稟議書.xdw: a faithful conversion has 163 page(s)  (157 preview entr(y/ies) must not appear)

$ N=$(pdfinfo 稟議書.pdf | awk '/^Pages/{print $2}')
$ xdw-salvage verify 稟議書.xdw --pages $N
稟議書.xdw: container 163 page(s), converted file 163 page(s)
  OK: page counts agree
```

落ちていれば報告し、終了コード 1 を返すのでバッチに組み込めます。

```
  ! page count: container says 163, converted file has 100 (63 missing)
```

`triage` は **`blank_pages` 列**を出します。**版面も図版もどちらも戻らない＝出力が完全に白紙になるページ**の数です。
移行の規模を測るとき効くのはこの数字で、「劣化するページ」ではなく「消えるページ」を数えます。
手元の 28 文書 1,406 ページでは **1,374 ページ（98%）が白紙**になります。
実機と照合済みの 2 文書でも、文書 C が 2 ページ中 1、文書 D が 4 ページ中 1 で、**どちらも実際の内容と一致**しました。

ページ数が合わない原因が「変換ソフトが縮小画像をページとして出力した」場合は、そう名指しします。`manifest -o out.csv` は 1 ページ 1 行の CSV（ページ番号・格納形式・用紙寸法 mm）を出すので、寸法の突き合わせを自前のパイプラインで行えます。

`pdfinfo` / `qpdf --show-npages` / `pdftk dump_data` など、ページ数が取れれば何でも構いません。

## コンテナの構造（要点）

- 要素は `[tag 1B][length][value]` の並び。length は BER と同じ規則（`0x00–0x7F` はその値、`0x8N` は続く N バイトをビッグエンディアンで読む）
- 読み出しは**末尾から**。ファイル末尾の 6 バイトがトレーラ自身の長さを指し、トレーラ内のページ絶対オフセット表から各ページに到達する
- 上書き保存は PDF の増分更新と同じで、末尾にトレーラを追記する。**最後のトレーラだけが現在の文書を表す**ため、先頭から読むのは等価ではない
- トレーラのタグはコンテナ世代によって変わる
- 外側の要素が申告する長さは**当てになりません**。実ファイルに、生きているトレーラが
  外側要素の申告範囲の外に出ているものがあります。先頭から読むと 1 ページも見つかりませんが、
  末尾から読む限り関係ありません
- **ページ表そのものが当てにならないファイルもあります**。実ファイル 2 件で、トレーラが
  ディスク上のファイルより長い文書を記述しており、オフセットが全部外れていました。
  この場合は拒否せず、**ファイルを走査してページ要素を直接見つけ**、その旨を報告します
  （上書き保存された文書では、過去の版のページも拾うことになります）

`info` は解釈できないタグを必ず報告します。手元の文書に未知の機能が入っていれば、そこに現れます。
なお手元の 20 ファイルでは**解釈できないコンテナ要素はゼロ**でした。
PDF の `/Contents` にあたる別立てのテキスト層は存在せず、文字は符号化されたページデータの中にあります。

### 壊れた入力について

移行ツールは、誰も中身を見ていないファイルを何千件も食わされます。**途中でパニックするツールは、
読めないと報告するツールより悪い**ので、どんな入力でも「解析に成功する」か「エラーを返す」かのどちらかで、
パニックも無限ループも青天井の確保もしない、という契約にしています。テストでは、正常なコンテナを
1 ビットずつ壊す・あらゆる位置で切り詰める・無作為に書き潰す・純粋な乱数を食わせる、を機械的に回しています。

### これから作る文書について

ページの圧縮方式は**選べます**。公開されている自動化ツールの資料によれば、選択肢には
PACKBITS・G4・外部 JPEG・圧縮なし・MRC 各種といった**普通のコーデック**が並んでいます。
手元のサンプルはすべて独自方式（圧縮方式フィールドの値 1）でしたが、
**取り込み時に標準コーデック側を選べば、最初から移植可能な文書になります。**
既存資産には効きませんが、読めない資産を増やし続けるのは止められます。

`info` は各ページの圧縮方式の値を必ず表示し、値 1 以外なら
「標準コーデックかもしれない」と明示します。

### 「標準の圧縮では」という筋について

プリンタドライバ由来なら標準形式では、という当たり前の筋は潰してあります。
LZNT1（`RtlCompressBuffer`）・PKWARE DCL Implode・Xpress Huffman・deflate は**固定ヘッダが合わず**、
MS-XCA Xpress・Hifn LZS・LZ4 は実装して当てて**目標長に届きません**。

さらに、展開後のデータ自体が**マジックナンバーを持つ標準形式ではない**ことが分かっています
（同じ展開後サイズのページ対 35 組で、出力の一致は中央値 7 ビット・最大 66 ビット。
EMF なら同じ用紙のページは先頭 384 ビットが一致するはずです）。

### 符号化について、今回分かったこと

ベンダー製 PDF を 1 冊分いただけたので、**中身が分かっているストリーム**が初めて手に入りました。

表紙（全面が大理石調の地紋）と 2 ページ目（全面テキスト、上下に大きな余白）の縮小画像は、
平文の先頭バイトがそれぞれ **0xAD（灰色）** と **0xD7（白、2,297 バイト連続）** だと確定します。

符号列の先頭 3 ビットは、前者が `100`、後者が `011` でした。
そこで縮小画像 **1,439 本すべて**を先頭 3 ビットで分類すると、

| 先頭 3 ビット | 本数 | 出どころ |
|---|---|---|
| `011` / `010` | 1,432 | 白地のテキスト文書 |
| **`100`** | **7** | **全部がカラーパンフレットの表紙** |

**`100` で始まる 7 本は例外なく全面写真の表紙**で、白地の文書からは 1 本も出ません。

つまり**先頭の符号語は先頭の画素に追随している** —— すなわち
**符号化器は毎回同じ初期状態から始まっている**ということです。
これは長く**仮定**でしかなく（「展開後は EMF ではない」の議論はこの仮定の上に立っていました）、
今回初めて実測で裏が取れました。

**まだ描けていないもの。** グラデーションのロゴ文字（WordArt）は、メーカー private の
コメントに**輪郭データ**として入っています（文字としては入っていません）。
場所と構造はほぼ解読できていて、差分列の復号ではストリームが 100% ちょうど消費されますが、
**約 28% のレコードで輪郭が壊れます**。中途半端に塗るとページを汚すので、
**シェイプマスクを宣言しているページでは塗りを描かない**方針にしています。
手元では 91,877 件中 345 件（0.4%、1 ページ）だけが該当します。詳細は `docs/coding.md` 9 節。

**測定上の落とし穴も記録しておきます。** 仮想プリンタ経由の PDF は四辺に印字不能余白を足すので
（実測で 150 dpi 約 27 px ≒ 縮小画像の約 2 行）、そのまま縮めると**文書に無い白**が先頭に付き、
全面写真の表紙まで白で始まっているように見えます。**四辺の白枠を測って切り落としてから**縮めてください。
一度これで誤った結論を出しました。

## 由来と方針

実ファイルの観察と、公開されているインターフェース仕様の意味論をもとに、**独自に書いたコード**です。

- ベンダーのコード・ヘッダ・バイナリを一切含まず、再配布もしません
- ベンダーのバイナリを逆アセンブル・逆コンパイルしていません
- ベンダーの文書・図・表を転載していません
- アクセス制御を迂回する機能はありません
- 本クレートにサンプル文書を同梱していません。テストはすべてテスト内で合成したバイト列に対して実行します

第三者の `.xdw` をテスト用に公開する場合は、自分で作成したファイルか、再配布が明示的に許可されたものだけを使ってください。

## Summary in English

Reads the container structure of DocuWorks `.xdw` files and salvages what can be recovered without the vendor's software: JPEG pages byte for byte, embedded original office files, and a PDF or a self-contained HTML page assembled from them. Pages written by the vendor's printer driver hold their image in a proprietary coding that this crate does not decode and reports honestly. Protected and signed documents are refused; no access-control bypass is implemented.

An independent implementation written from observed file behaviour and publicly documented interface semantics. Contains no vendor code, headers, binaries or documentation, and none were disassembled. Not affiliated with or endorsed by FUJIFILM Business Innovation.
